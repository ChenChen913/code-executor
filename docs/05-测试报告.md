### 关于"加固参数的回归保护"

`SandboxPolicyTest` 里的断言看起来像"把代码抄了一遍"，但它们真正的用途是**回归保护**：

```java
@Test
void networkIsDisabled() {
    assertThat(policy.hostConfig(pythonSpec()).getNetworkMode()).isEqualTo("none");
}
```

以后有人为了图方便删掉 `--network none`，**测试会直接红掉**。

> 加固配置最怕的就是被"顺手简化"——它平时不产生任何可见效果，
> 删掉之后一切照常运行，直到出事。必须有东西拦着。

## 4. 测试中发现并修复的 5 个缺陷

**这一节是整份报告最有价值的部分。**

这 4 个缺陷**全部**是"纸面设计正确、单元测试通过、但真实运行失败"的类型。
它们说明了为什么"代码写完了"和"项目做完了"是两件事。

### 缺陷 1：Docker 客户端缺传输层，第一次执行就崩

| | |
|---|---|
| **现象** | 第一次执行代码 → HTTP **500** |
| **错误** | `NullPointerException: dockerCmdExecFactory was not specified` at `DockerClientImpl.createContainerCmd` |
| **根因** | docker-java 3.7 的 `DockerClientImpl.getInstance(config)` **不会**自动装配传输层。用它拿到的客户端能创建 Bean、能启动应用、演练模式下毫无问题——但第一次真正下发命令时就 NPE |
| **修复** | 显式构造 `ZerodepDockerHttpClient` 并传入 `getInstance(config, httpClient)` |
| **顺带改进** | 从聚合包 `docker-java` 换成 `docker-java-core` + `docker-java-transport-zerodep`（自包含、依赖全部 relocate 过），避免 jersey 自带一份 Jackson 和 Spring Boot 打架 |
| **为什么单元测试没发现** | 单元测试和演练模式都不碰 Docker，这条路径根本没被执行 |

### 缺陷 2：`docker cp` 被只读根文件系统拒绝

| | |
|---|---|
| **现象** | 修完缺陷 1 后 → HTTP **503** |
| **错误** | `Status 400: {"message":"container rootfs is marked read-only"}` |
| **根因** | `docker cp` **不是**通过容器的挂载命名空间写的，而是 Docker 守护进程按"rootfs 里的路径"写的。守护进程眼里的 rootfs 是只读的镜像层，**它看不到容器内部挂的 tmpfs**——所以工作目录明明可写，它照样被拒绝 |
| **修复** | 改用 `docker exec`（容器视角）把代码写进去 |
| **为什么单元测试没发现** | 这是 Docker 的运行时行为，不是 API 签名问题 |

> **这条教训值得单独记**：`docker cp` 和 `docker exec` 看起来都是"操作容器里的文件"，
> 但它们走的是**两条完全不同的路**。前者是守护进程视角，后者是容器视角。

### 缺陷 3：docker-java 的 exec stdin 会死等

| | |
|---|---|
| **现象** | 改用 exec 写文件后 → 每次都 `把源码写入容器超时（10000ms）` |
| **根因** | docker-java 的 `ExecStartCmd.withStdIn(...)` 配合 `awaitCompletion(...)` 会一直挂住：stdin 写完之后 `cat` 等不到 EOF，两边互相等 |
| **尝试** | 用命令行 `docker exec -i ... sh -c 'cat > f'` 手动验证是**可以**的 → 说明是 docker-java 这一层的问题，不是 Docker 的问题 |
| **修复** | 换一条确定能走通的路：**base64 走命令行参数**，`sh -c 'printf %s "$1" \| base64 -d > "$2"'`。源码作为独立的 argv 元素，不经过 shell 解析 |
| **附带好处** | 注入面为零——base64 字母表不含任何 shell 元字符。实测传 `/workspace/a;id` 只会创建一个叫 `a;id` 的文件 |
| **代价** | 源码 base64 后膨胀 1/3，受 Linux 单参数 128 KiB 限制，所以代码上限不能超过约 90 KB（已加显式校验和友好报错） |

### 缺陷 4：DNS 解析耗光整个运行超时

| | |
|---|---|
| **现象** | 安全测试里 DNS 那项失败：`stdout` 为空，状态是 `TIMEOUT` |
| **根因** | `--network none` 之后 Docker **仍然**会把宿主机的 nameserver 写进容器的 `/etc/resolv.conf`，而那个地址根本路由不到，于是解析一直重试到耗尽运行超时 |
| **隐藏问题** | 那行配置本身就是**信息泄露**——用户代码 `cat /etc/resolv.conf` 就能读到宿主机的内部 DNS 地址 |
| **修复（部分）** | 加 `--dns 127.0.0.1`，消除信息泄露 |
| **没修复的部分** | **没有**让解析"快速失败"。试过 `--dns`，但 musl（Alpine）会按自己的重试节奏一直等到超时 |
| **处理方式** | ① 把代码注释改成实话，不写"会快速失败"这种做不到的承诺；<br>② 把测试断言改成断言**真正的安全属性**（"解析不出来"），而不是我原本想要的副作用 |
| **教训** | 如果当时把测试改成"能过就行"，就会在代码里留下一条**说谎的注释**。宁可让测试断言弱一点，也不能让注释和实际行为不一致 |

> **关于缺陷 4 的取舍值得说明**：`--dns 127.0.0.1` 没能实现我原本想要的效果，
> 但它确实解决了另一个真实问题（信息泄露），所以**保留**——
> 只是注释必须诚实地说明它做到了什么、没做到什么。

### 缺陷 5：Docker 挂掉时返回 500 而不是 503

这个缺陷是**在做鉴权测试时偶然撞出来的**：Docker Desktop 恰好自己停了，
于是"带正确 key"那条断言拿到了 500 而不是预期的 200。

| | |
|---|---|
| **现象** | Docker 守护进程不可达时，接口返回 `500 执行器内部错误：RuntimeException` |
| **应该是** | `503`（沙箱不可用）——这两者对调用方的含义**完全不同**：<br>500 让人以为是自己代码或服务端 bug，503 才正确表达"环境没准备好，别重试" |
| **根因** | 守护进程连不上时，docker-java 抛的是【**裸 `RuntimeException` 包着一个 `IOException`**】：<br>`java.lang.RuntimeException: java.nio.file.NoSuchFileException: \\.\pipe\dockerDesktopLinuxEngine`<br>它不是 `DockerException`，所以原来那两个 catch 都接不住 |
| **修复** | 增加一个兜底分支，用**因果链里有没有 `IOException`** 来区分"环境问题"和"代码 bug"：<br>有 → 503；没有 → 继续上抛，交给 500 |
| **为什么用 IO 异常做判据** | docker-java 在这里的异常层次不统一（有时 `DockerException`，有时裸 `RuntimeException` 包 `NoSuchFileException`/`ConnectException`/`SocketException`），但这几个都是 `IOException` 的子类。这个判据顺带把两类问题分开了 |
| **验证方式** | 不重启 Docker，而是把应用指到一个不存在的 pipe：<br>`--executor.docker.host=npipe:////./pipe/does-not-exist`<br>结果：`503 连不上 Docker 守护进程：\\.\pipe\does-not-exist` ✅ |
| **回归保护** | `DockerCodeRunnerFailureClassificationTest` 7 个用例，含"因果链成环"和"代码 bug 不能被误判成环境问题" |

> **这个缺陷的发现方式本身就是一条教训**：
> 前 4 个缺陷是靠"主动去跑"发现的，这一个是靠"**环境恰好坏了**"发现的。
> 如果当时 Docker 一直正常，这个 bug 会一直躺在代码里，
> 等到线上 Docker 重启时才以"500 内部错误"的形式爆发，
> 把排查方向引向完全错误的地方。

## 5. 没测到的部分

**测试报告如果不写"没测什么"，就没有可信度。**

| # | 没测的 | 风险 |
|---|---|---|
| 1 | **压测 / 性能** | 并发上限 4 是拍脑袋定的，没有数字支撑；单机 QPS 未知；**这是最大的空白** |
| 2 | **多节点 / Linux 宿主机** | 本次验证在 Windows + Docker Desktop 上做。Linux 上的 seccomp 行为、cgroup v1/v2 差异都没覆盖 |
| 3 | **真实攻击测试** | 只验证了"配置按预期生效"，**没有尝试过内核漏洞利用、容器逃逸** |
| 4 | **长时间运行** | 回收器验证了一轮，没跑过"连续 24 小时"的泄漏检查 |
| 5 | **并发正确性** | 没有验证"4 个请求同时到达"时信号量行为是否正确 |
| 6 | **异常路径** | 没测过"执行到一半 Docker 挂了"、"磁盘满了"、"镜像被人删了" |
| 7 | **大代码量** | 没测过接近 64 KB 上限的代码 |
| 8 | **二进制输出** | 用户代码输出非 UTF-8 字节时的行为没验证 |

## 6. 怎么复现

### 前置

```bash
# 1. 确保 Docker 可用
docker ps

# 2. 构建运行镜像（国内需要配镜像加速，见部署文档第 1 节）
docker build -t code-executor-runner:1 .
```

### 跑单元测试

```bash
mvn test
```

### 跑真实端到端测试

```bash
# 终端 1
mvn spring-boot:run

# 终端 2
pwsh -File scripts/e2e-test.ps1            # Linux / macOS
powershell -File scripts/e2e-test.ps1      # Windows
```

脚本是**幂等**的，可以反复跑。它会：

1. 检查前置条件（执行器、Docker、镜像）
2. 依次提交 18 段代码，逐条断言
3. 检查有没有残留容器
4. 打印通过/失败汇总，失败时以非 0 退出码结束（可以直接接进 CI）

### 只验证安全部分

想快速确认"沙箱还是关着的"，跑这三条就够：

```bash
# 断网
curl -s -X POST http://localhost:8080/api/v1/executions -H 'Content-Type: application/json' \
  -d '{"language":"python","code":"import socket\nprint(socket.gethostbyname(\"baidu.com\"))"}'
# 期望：解析不出来（TIMEOUT 或报错），绝不能返回 IP

# 只读根文件系统
curl -s -X POST http://localhost:8080/api/v1/executions -H 'Content-Type: application/json' \
  -d '{"language":"python","code":"open(\"/etc/x\",\"w\").write(\"x\")"}'
# 期望：RUNTIME_ERROR，stderr 含 Read-only file system

# 非 root
curl -s -X POST http://localhost:8080/api/v1/executions -H 'Content-Type: application/json' \
  -d '{"language":"python","code":"import os; print(os.getuid())"}'
# 期望：stdout 是 10001，不是 0
```
