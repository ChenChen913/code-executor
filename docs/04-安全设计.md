## 1. 威胁模型

### 我们在保护什么

| 资产 | 泄露/损坏的后果 |
|---|---|
| **宿主机** | 最严重。宿主机上可能还有别的服务、数据库 |
| **执行器进程自身** | 被打挂 = 服务不可用 |
| **同机的其他容器** | 横向移动的跳板 |
| **内网其他服务** | 用户代码可以拿它当跳板去探测 |
| **宿主机磁盘上的文件** | 项目配置、数据库密码 |

### 我们在防谁

**假设攻击者能完全控制提交的代码。** 这条假设很重要——它意味着：

- ❌ 不能靠"看起来危险就拒绝"（黑名单永远不全）
- ❌ 不能靠"检查代码里有没有 `os.system`"（绕过方式无穷多）
- ✅ 只能靠**"就算代码是恶意的，它也做不了什么"**

这是本项目和"用正则过滤关键字"那类方案的根本区别。

### 不在防护范围内

明确不防的，免得产生虚假的安全感：

- **不防"合法的资源消耗"**。用户可以提交一段需要跑 5 秒的正当代码，这不是攻击
- **不防高级持续性威胁（APT）**。没有做内核级对抗
- **不防 Docker 本身的 0day**。容器共享宿主内核，这是根本性的局限
- **不防内部人员**。谁能改配置文件，谁就能关掉所有加固

## 2. 信任边界

```
┌─────────────────────────────────────────────────────────┐
│  不可信区域：用户代码                                     │
│  ┌───────────────────────────────────────────────────┐  │
│  │  容器（加固过的）                                   │  │
│  │  · 无网络  · 只读根文件系统  · 非 root             │  │
│  │  · 无特权  · 内存/CPU/进程数 全受限                │  │
│  │  唯一可写：/workspace 和 /tmp（都是内存盘）         │  │
│  └───────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
              ▲ 只允许：写入代码、执行命令、读取输出
              │ （全部经由 Docker API，参数以数组传递，无 shell 中转）
┌─────────────┴───────────────────────────────────────────┐
│  可信区域：执行器进程                                     │
│  · 持有 Docker socket 访问权（≈ 宿主机 root）            │
│  · 目前【没有鉴权】—— 这是最大的未解决风险                │
└─────────────────────────────────────────────────────────┘
```

**这张图里最关键的一点**：

> 执行器持有 Docker socket，而 Docker socket 等价于宿主机 root。
> 所以"能调执行器接口" ≈ "拥有宿主机 root"。

**本项目的加固全部集中在上面那个框（容器），
但没有解决下面那个框（谁能调接口）。** 见[残余风险](#4-残余风险诚实清单)第 1 条。

## 3. 加固清单与实测证据

下面每一条都是**在本项目上真实跑出来的**结果，
不是"照着文档写了参数"而已。复现命令见 [测试报告](05-测试报告.md)。

### 3.1 网络隔离

| 配置 | `--network none` + `--dns 127.0.0.1` |
|---|---|
| **挡住** | SSRF 探测内网、外传数据、挖矿、把服务当代理 |
| **实测** | 用户代码 `socket.create_connection(("1.1.1.1", 53))` → `OSError`（连不上） |
| **实测** | `socket.gethostbyname("www.baidu.com")` → 解析不出来 |
| **实测** | 容器内 `/etc/resolv.conf` 是 `nameserver 127.0.0.1`，**不泄露宿主机 DNS 地址** |

> **为什么 `--dns 127.0.0.1`？** 因为断网之后 Docker **仍然**会把宿主机的 nameserver
> 写进容器的 `/etc/resolv.conf`。用户代码 `cat` 一下就能读到宿主机的内部 DNS 地址——
> 这是一条不起眼但真实的信息泄露。

### 3.2 文件系统

| 配置 | `--read-only` + 两个 tmpfs |
|---|---|
| **挡住** | 改 `/etc`、装后门、写 crontab、写满磁盘 |
| **实测** | 写 `/etc/evil.conf` → `OSError: Read-only file system` |
| **实测** | 写 `/workspace/probe.txt` → **成功**（沙箱不是"什么都不让干"） |

唯一可写的地方是 `/workspace` 和 `/tmp`，都是 **tmpfs（内存盘）**——
容器一停，里面所有东西自动消失，宿主机磁盘上不留痕迹。

### 3.3 权限

| 配置 | `--user 10001:10001` + `--cap-drop ALL` + `no-new-privileges` |
|---|---|
| **挡住** | 大多数提权路径、挂载、改网络、改时间、加载内核模块 |
| **实测** | `os.getuid()` → **10001**（不是 0） |
| **实测** | 直接调 `mount()` 系统调用 → `MOUNT_DENIED`（特权已丢） |

**为什么非 root 这么重要？** 因为容器内的 root + 任意一个内核漏洞 = 宿主机的 root。
非 root 让这条链路多了一道门槛。

### 3.4 资源限制

| 配置 | `--memory` + `--memory-swap`（相等）+ `--cpus 1` + `--pids-limit` + `ulimit` |
|---|---|
| **挡住** | 内存炸弹、CPU 挖矿、fork 炸弹、句柄耗尽 |
| **实测** | 不断申请 50MB 内存 → `OUT_OF_MEMORY`，退出码 137，容器被内核杀掉 |
| **实测** | `while True: pass` → `TIMEOUT`（5 秒后容器被终止） |
| **实测** | 循环 `os.fork()` → 第 **30** 个进程被拒（`[Errno 11] Resource temporarily unavailable`） |

> **`--memory-swap` 必须和 `--memory` 相等。**
> 否则内存超限会被 swap 悄悄吃掉，表现为"慢得要死"而不是"被杀"——
> 那更难发现，也更难排查。
>
> **fork 炸弹是最容易被忽略的一种攻击**：它不占内存（每个进程很小）、
> 不超时（一直在正常 fork）、不越权（就是创建进程），
> 但能在 1 秒内耗尽宿主机的进程表。**只有 pids 限制能挡。**

### 3.5 输出限制

| 机制 | 应用层 64 KB 上限 + `truncated` 标记 |
|---|---|
| **挡住** | `while True: print("x"*1000)` 打爆**执行器自己**的内存 |
| **实测** | 输出 5MB → 只回传 65536 字节，`truncated: true` |

**这是唯一一条防"用户代码伤害执行器本身"而不是"伤害宿主机"的措施。**
它看起来不危险，实际上是唯一能直接打死执行器的一条。

技术细节：超限之后**仍然继续把流读干净**（只是不存），
否则写端会因为管道写满而阻塞，进程反而永远退不出来——
那就从"内存被打爆"变成"线程被挂死"，更糟。

### 3.6 命令注入

| 机制 | 命令一律用数组传递；源码走 base64 参数 |
|---|---|
| **挡住** | 通过拼接参数注入额外命令 |
| **实测** | 把 `/workspace/a;id` 当文件名传进去 → 创建了**名字叫 `a;id` 的文件**，没有执行 `id` |

三个东西各走各的通道，谁也污染不了谁：

| 内容 | 通道 | 为什么安全 |
|---|---|---|
| 脚本 | 常量字符串 | 没有任何拼接 |
| 源码 | `$1`，base64 | base64 字母表不含任何 shell 元字符 |
| 文件名 | `$2`，配置校验过 | 不含 `/` `\` `..`，且不是用户可控的 |

### 3.7 清理（防"慢性失血"）

这一条不防攻击，防的是**自己把自己耗死**。三层防御：

| 层 | 机制 | 实测 |
|---|---|---|
| 1 | `try / finally` 显式删容器 | 28 项测试跑完，**残留 0 个容器** |
| 2 | 容器自带"保命时长"（`sleep 编译超时+运行超时+30s`） | 执行器被 `kill -9` 也不会永久泄漏 |
| 3 | 定时扫标签回收 | 造一个 1 小时前创建的受管容器 → **被回收**；同时新创建的容器 → **被保护期保住，没被误删** |

第 2 层是"保命"设计：容器的常驻命令不是 `sleep infinity`，而是一个有上限的值。
正常流程里执行器会提前删掉它；但如果执行器进程被杀、机器断电，
**容器最多多活几十秒就会自己退出**。

## 4. 残余风险（诚实清单）

安全文档如果只列"防住了什么"，就没有可信度。以下是**明确知道还没解决**的：

### 🔴 高风险

| # | 风险 | 影响 | 缓解 | 计划 |
|---|---|---|---|---|
| 1 | **没有鉴权** | 任何能访问 8080 的人都能执行代码；而执行器持有 Docker socket ≈ **宿主机 root** | 只能用防火墙限制来源，**绝不能暴露公网** | M2 |

### 🟠 中风险

| # | 风险 | 影响 | 缓解 | 计划 |
|---|---|---|---|---|
| 2 | **只读根文件系统仍然可读系统文件** | 用户代码能读到镜像里的 `/etc/passwd`、`/etc/os-release` 等。**数据出不去（断网），但信息会被看到** | 断网让泄露失去意义；可用更精简的基础镜像进一步缩小可读面 | M2 |
| 3 | **seccomp 用的是 Docker 默认 profile** | 系统调用层面的防护比自定义 profile 弱。Docker 默认已禁掉约 44 个危险调用，但不是最小权限 | 无 | M2：自定义 profile |
| 4 | **容器共享宿主内核** | 内核漏洞 = 容器逃逸。这是所有容器方案的共同局限 | 及时打内核补丁 | M3：gVisor / Kata |
| 5 | **执行器和 Docker 同机** | 隔离性弱于独立节点 | 无 | M2：独立节点 |
| 6 | **没有资源配额（quota）** | 只有一个全局并发上限，无法限制"某个调用方一天用多少" | 无 | M2 |

### 🟡 低风险 / 已知不便

| # | 风险 | 说明 |
|---|---|---|
| 7 | 未使用 `--init` | 容器 PID 1 是 `sleep`，不回收僵尸进程。因为一请求一容器、最多 exec 3 次，影响可忽略。**生产环境建议加上**（注意：需要宿主机装了 `docker-init`） |
| 8 | 域名解析会耗光运行超时 | 见[部署文档的排查章节](02-部署文档.md#为什么域名解析会导致-timeout-而不是报错)。安全属性成立，只是错误信息不友好 |
| 9 | 没有做真实攻击测试 | 上面所有"实测"都是验证"配置按预期生效"，**没有尝试过真正的对抗**（内核漏洞利用、容器逃逸） |

## 5. 部署侧的安全要求

代码里的加固只覆盖了一半。**另一半在部署方式上**：

### ✅ 必须做

1. **不要暴露到公网。** 没有鉴权，这是硬要求
2. **不要容器化执行器 + 挂 `docker.sock`。** 那等于把宿主机 root 交出去。
   详见[部署文档第 7 节](02-部署文档.md#7-️-一个必须知道的安全红线)
3. **执行器与主业务、数据库物理隔离。** 不要在同一台机器上
4. **及时更新宿主机内核和 Docker。** 容器共享内核，内核补丁就是安全边界
5. **限制 Docker socket 的访问权限**（`docker` 组只放必要的人）

### ✅ 建议做

6. 系统防火墙只放行内网可信来源到 8080
7. 给执行器进程加 systemd 加固（`NoNewPrivileges` / `ProtectSystem` 等，见部署文档）
8. 监控孤儿容器数量、执行失败率、容器创建耗时
9. 定期 `docker system prune`，并确认回收器在工作
10. 给 `/api/v1/executions` 加一层网关级的限流，作为应用内限流的补充

## 6. 出了问题怎么排查

每次执行都有一个 `jobId`，它会写进容器的标签。
即使用户没记，日志里也有。

```bash
# 1. 找日志里对应的那次执行
grep "job=<jobId>" app.log

# 2. 看有没有残留的容器
docker ps -a --filter label=code-executor.managed=true

# 3. 看某个容器的完整配置（确认加固参数真的生效了）
docker inspect <containerId> | grep -A5 HostConfig

# 4. 看它是不是被 OOM 杀的
docker inspect <containerId> --format '{{.State.OOMKilled}} {{.State.ExitCode}}'
```

**如果怀疑被攻击了**：

1. 立刻停掉执行器（`systemctl stop code-executor`）——**这会切断攻击者的入口**
2. `docker ps -a` 看有没有可疑容器
3. 检查宿主机：`last`、`/var/log/auth.log`、有没有新增用户或 crontab
4. 检查 Docker socket 有没有被挂载进任何容器：`docker ps -a --format '{{.Names}}' | xargs -I{} docker inspect {} --format '{{.Name}} {{.HostConfig.Binds}}'`
