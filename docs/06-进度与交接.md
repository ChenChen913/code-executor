## 四、接着做时的注意事项

- **每次改完都要跑两遍验证**：`mvn -B test`（115 个单测）+ `scripts/e2e-test.ps1`（53 项真容器断言）。
  单测过了不代表真容器能跑——本次开发中好几个 bug 只有真容器测试才暴露
- **改 `.ps1` 之后必须重新存成「UTF-8 带 BOM」**。PowerShell 5.1 会按 ANSI 读 `.ps1`，
  中文注释会让脚本解析失败，报错是莫名其妙的 `意外的标记 "[PASS]"`：
  ```powershell
  $c = [System.IO.File]::ReadAllText($p, [System.Text.UTF8Encoding]::new($false))
  [System.IO.File]::WriteAllText($p, $c, [System.Text.UTF8Encoding]::new($true))
  ```
- **`scripts/start.ps1` 里 `$ErrorActionPreference` 必须是 `Continue`**。设成 `Stop` 会在
  `java -version`（它往 stderr 写东西）那一步就整个脚本挂掉
- **改 Dockerfile 后要重新 build 镜像**，否则测的还是旧镜像
- PowerShell 里 `$host`、`$user` 是只读自动变量，别拿来当变量名
- 启动日志别写进 `target/`：`mvn clean` 会因为它被占用而失败。用 `%TEMP%`

## 五、本次开发中踩到并修掉的真实 bug（对维护者最有价值的部分）

按"如果不实测就绝对发现不了"排序：

### 1. 回收器在杀正在执行的请求 ⚠️ 最危险

加了"预热池对账"（把名字像预热容器、却不在池子记账里的容器当泄漏删掉）之后，
**预热容器一旦被租用，它就不在池子的队列里了** —— 于是被当成泄漏当场删掉，
删的正是当前这次执行。

表现极具迷惑性：**死循环程序跑 2 秒就返回 `RUNTIME_ERROR`（被 SIGKILL），
单独测又完全正常**。因为回收器每 60 秒才跑一轮，要赶上正好。

修法：池子维护一份"已租出"登记，`isInUse()` 同时覆盖「池中待用」和「已租出正在用」，
回收器一律跳过。**没有这个登记，回收器还会因为"预热容器存活 300 秒 > 120 秒保护期"而误杀。**

### 2. `@RestControllerAdvice` 捕获不到 Filter 抛的异常

配额超限时返回的是 **500（执行器内部错误）而不是 429**。
`@RestControllerAdvice` 只作用于 Controller 层，过滤器里抛出的异常直接冒到 Servlet 容器。
修法：过滤器自己写错误响应，格式与全局错误处理保持一致。

### 3. 预热池缓慢累积容器

定时补充和"取走即补"是两条独立路径，并发跑时各自看到"池子还是空的"，于是各创建一个。
实测出现 `warm-per-language=1` 却有 2 个 Java 容器。这种慢慢累积的泄漏在生产上极难查。
修法：每语言一把互斥（`refilling` 集合）。

另外还发现两处泄漏点：`acquire()` 判定容器已死时**只从队列摘掉、没销毁**；
`release()` **没检查容量**。两处都已修，并且加了对账兜底（见下）。

### 4. Docker 分层导致"删了等于没删"

最小化镜像时在后续层 `rm -rf` 掉几百 MB，`docker images` 一看**一个字节都没少**——
被删的文件仍然完整地留在下面那几层里。
修法：`FROM scratch` + `COPY --from=runner-minimal / /` 把文件系统拍平。
代价：`scratch` 不带任何 `ENV`，基础镜像原本的 `JAVA_HOME` / `PATH` 全丢了，
表现为 **`java: not found` 而 python/node 正常**，必须显式补回来。

### 5. 容器连不上 Docker 守护进程被报成 500 而不是 503

docker-java 在这种情况下抛的是**裸 `RuntimeException` 包着 `NoSuchFileException`**，
不是 `DockerException`，常规的异常分类接不住。
判据改成"因果链里有没有 `IOException`"，顺带把「环境问题」（该 503）
和「代码 bug」（该 500）分开了。

### 6. 其他

- `python3 -I` 会顺带开 `-P`，把脚本目录从 `sys.path` 里去掉，导致 `import helper` 失败 → 改用 `-E -s`
- 我自己写的测试不可靠：TTL 设成 0 时 `finishedAt` 和 `cutoff` 可能落在同一时钟刻度，
  `isBefore` 为假，测试变成看运气 → 改用负 TTL 让它确定性过期
- 错误信息里把"分钟"打成了繁体"分**鐘**"，被测试断言抓出来

### 关键设计决定（改之前先读，否则容易改坏）

1. **一请求一容器，绝不复用。** 预热池里只放"从未被使用过"的容器，用完照旧销毁。
   复用型池子能多省几十毫秒的销毁时间，但会让容器跨请求存活，
   引入跨用户的状态泄漏风险——这个交换不划算。
2. **不做 webhook。** 执行器跑在内网且持有 `docker.sock`，
   让它主动 POST 到调用方指定的 URL 是现成的 SSRF 通道。
3. **指标标签只用 `language` 和 `status`。** 绝不把 jobId、调用方名字做成标签——
   那是 Prometheus 内存爆炸的经典原因。调用方维度走配额和审计日志。
4. **隔离性优先于性能。** 每一处性能优化都要能说清"它没有削弱隔离"，
   否则不做。预热池和编译缓存都是按这个标准筛过的。
