| 方法 | 路径 | 需要鉴权 | 说明 |
|---|---|---|---|
| `POST` | `/api/v1/executions` | ✅ | 执行一段代码 |
| `GET` | `/api/v1/languages` | ✅ | 查询支持的语言与配额 |
| `GET` | `/actuator/health` | ❌ | 健康检查 |

## 鉴权（必读）

**所有业务接口都需要 API Key。**

```
X-API-Key: <你的 key>
```

| 情况 | 结果 |
|---|---|
| 缺少请求头 | `401` `{"status":401,"message":"缺少 X-API-Key 请求头"}` |
| key 不正确 | `401` `{"status":401,"message":"API Key 无效"}` |
| 正确 | 正常处理 |

几个要点：

- **key 由服务端管理员发放**，通过环境变量注入，不在这个文档里
- 错误响应**不会回显你提交的 key**（连前缀都不回显）
- `/actuator/health` 免鉴权，方便负载均衡器探活
- **不要依赖 IP 白名单做鉴权**——如果前面有反向代理，
  `X-Forwarded-For` 是客户端可以伪造的；服务端只用它写日志，不用它做判断

```bash
# 正确的调用姿势
curl -X POST http://localhost:8080/api/v1/executions \
  -H 'Content-Type: application/json' \
  -H "X-API-Key: $EXECUTOR_AUTH_KEYS_0_VALUE" \
  -d '{"language":"python","code":"print(1+1)"}'
```

## POST /api/v1/executions

执行一段代码。**一次请求 = 一个全新的、加固过的容器。**

### 请求体

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `language` | string | ✅ | 语言 id，见 `/api/v1/languages`。大小写和前后空格不敏感 |
| `code` | string | ✅ | 用户代码，UTF-8。上限见 `executor.max-code-bytes`（默认 64 KB） |

```json
{
  "language": "python",
  "code": "print(1 + 1)"
}
```

**v1 刻意不支持的**：`stdin`、多文件、自定义编译/运行参数。
每多一个用户可控的输入，就多一条要防守的路径。

### 响应体

```json
{
  "jobId": "63ceae09-f0fa-4562-aed1-bd8cb277175a",
  "language": "python",
  "status": "SUCCESS",
  "success": true,
  "exitCode": 0,
  "stdout": "2\n",
  "stderr": "",
  "compileOutput": null,
  "truncated": false,
  "timedOut": false,
  "durationMs": 442,
  "message": "运行成功"
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `jobId` | string | 本次执行 id。**排查问题时把它给运维**，可以用它去捞对应容器 |
| `language` | string | 实际使用的语言 id |
| `status` | enum | 见[执行状态全表](#执行状态全表) |
| `success` | boolean | 仅当 `status == "SUCCESS"` 时为 `true` |
| `exitCode` | int \| null | **运行阶段**的退出码。编译失败时是编译阶段的退出码 |
| `stdout` | string | 运行阶段的标准输出（可能被截断） |
| `stderr` | string | 运行阶段的标准错误（可能被截断） |
| `compileOutput` | string \| null | **编译阶段**的输出（stdout + stderr 合并）。不需要编译的语言为 `null` |
| `truncated` | boolean | 输出被截断过。**为 `true` 时你看到的不是全部** |
| `timedOut` | boolean | 是否因超时被强制终止 |
| `durationMs` | long | 从创建容器到清理完成的耗时 |
| `message` | string | 人类可读的说明，适合直接展示给用户 |

### 为什么 `stdout` 和 `compileOutput` 要分开？

因为**用户最想知道的第一件事是"没编译过，还是跑起来挂了"**。
混在一起的话，用户面对一坨编译错误加运行输出，分不清哪句是自己程序的输出。

### 为什么必须看 `truncated`？

因为输出被截断而用户不知道，他会以为自己程序的输出就这么多。
**这比报错更糟**——报错至少知道自己错了。

## GET /api/v1/languages

查询当前支持哪些语言，以及各自的资源配额。

```bash
```bash
curl -H "X-API-Key: $EXECUTOR_AUTH_KEYS_0_VALUE" http://localhost:8080/api/v1/languages
```
```

```json
[
  {
    "id": "java",
    "displayName": "Java 17",
    "sourceFileName": "Main.java",
    "needsCompile": true,
    "compileTimeoutMs": 20000,
    "runTimeoutMs": 8000,
    "memoryMb": 256,
    "pidsLimit": 64
  },
  {
    "id": "python",
    "displayName": "Python 3",
    "sourceFileName": "main.py",
    "needsCompile": false,
    "compileTimeoutMs": 10000,
    "runTimeoutMs": 5000,
    "memoryMb": 128,
    "pidsLimit": 32
  }
]
```

> **注意这里没有返回 `compileCommand` / `runCommand`。**
> 容器内部的命令属于实现细节，暴露出去只会给攻击者提供信息。

### ⚠️ 关于 `sourceFileName`：Java 的类名必须匹配

`sourceFileName` 是代码在容器里**实际保存成的文件名**。
你的代码必须与之匹配：

| 语言 | 容器内文件名 | 你必须写 |
|---|---|---|
| Java | `Main.java` | `public class Main { ... }` ← **类名必须是 `Main`** |
| Python | `main.py` | 无要求 |
| JavaScript | `main.js` | 无要求 |

写成 `public class Solution` 会得到：

```
status: COMPILE_ERROR
compileOutput: "Main.java:1: error: class Solution is public, should be declared in a file named Solution.java"
```

> 有些在线执行器（比如菜鸟教程）会自动把类名替换成 `Main`。
> 本项目**不做**这种替换——用正则改用户的代码既脆弱又容易改错，
> 不如把规则明确写出来。

## GET /actuator/health

```bash
curl http://localhost:8080/actuator/health
```

```json
{ "status": "UP" }
```

> 这个接口**只反映执行器进程本身**，不反映 Docker 是否可用。
> Docker 的状态在启动日志里，以及每次执行请求的响应里。

---

## 状态码约定

**只要执行本身完成了，就返回 `200`** —— 哪怕用户代码编译失败、超时、被 OOM 杀掉。
这些都是"正常结果"，写在响应体的 `status` 字段里。

这样调用方**只需要解析一套语义**：

- **HTTP 状态码**回答"我的请求有没有被受理"
- **`status` 字段**回答"我的代码跑得怎么样"

| HTTP | 场景 | 调用方该怎么办 |
|---|---|---|
| `200` | 已执行（结果好坏看 `status`） | 解析 `status` |
| `400` | 语言不支持 / 代码为空 / 超长 / JSON 格式错 | **修请求，不要重试** |
| `401` | 缺少或错误的 `X-API-Key` | 检查凭据，**不要重试** |
| `429` | 并发已满 | 退避后重试 |
| `500` | 执行器内部错误 | 告警，附上 `jobId` |
| `503` | Docker 连不上 / 运行镜像没构建 | 告警，**不要重试** |

错误响应体统一是：

```json
{
  "status": 400,
  "message": "不支持的语言：cobol，当前支持 [java, python, javascript]"
}
```

## 执行状态全表

| `status` | 含义 | 用户该做什么 | 该看哪个字段 |
|---|---|---|---|
| `SUCCESS` | 跑完了，退出码 0 | —— | `stdout` |
| `COMPILE_ERROR` | 编译失败，**没有运行** | 改语法 / 改类型 | `compileOutput` |
| `RUNTIME_ERROR` | 编译过了，但进程非 0 退出 | 改逻辑 | `stderr` |
| `TIMEOUT` | 超过该语言的运行/编译超时，容器已被强制终止 | 查死循环；或申请更大配额 | `message` |
| `OUT_OF_MEMORY` | 超过内存上限，容器被内核杀掉 | 查数据量；或申请更大配额 | `message` |
| `DRY_RUN` | 演练模式，**没有真正执行** | —— | `stdout`（里面是渲染好的命令） |
| `INTERNAL_ERROR` | 执行器自身出问题 | 联系运维，提供 `jobId` | `message` |

### `TIMEOUT` 和 `OUT_OF_MEMORY` 为什么值得单独分出来？

因为这两个是**安全兜底**触发的，用户需要知道是"我的代码有问题"还是"配额太小"。
而且从退出码上几乎分不出来——两者都是 137 / SIGKILL。
只有 Docker 的 `OOMKilled` 标记能区分，所以本项目专门去查了它。

## 调用示例

### curl

```bash
curl -X POST http://localhost:8080/api/v1/executions \
  -H 'Content-Type: application/json' \
  -H "X-API-Key: $EXECUTOR_AUTH_KEYS_0_VALUE" \
  -d '{"language":"python","code":"print(1+1)"}'
```

> ⚠️ Windows 的 `cmd` 和 PowerShell 对 JSON 里的双引号处理很麻烦。
> 建议把请求体写进文件再 `-d @body.json`，本项目的 `scripts/e2e-test.ps1` 就是这么做的。

### Java（需要编译的语言）

```bash
curl -X POST http://localhost:8080/api/v1/executions \
  -H 'Content-Type: application/json' \
  -H "X-API-Key: $EXECUTOR_AUTH_KEYS_0_VALUE" \
  -d '{"language":"java","code":"public class Main { public static void main(String[] a){ System.out.println(\"hi\"); } }"}'
```

注意 `public class Main` —— 类名必须是 `Main`。

### Python

```python
import os
import requests

resp = requests.post(
    "http://localhost:8080/api/v1/executions",
    json={"language": "python", "code": "print(sum(range(101)))"},
    headers={"X-API-Key": os.environ["EXECUTOR_AUTH_KEYS_0_VALUE"]},
    timeout=60,
)

if resp.status_code == 401:
    raise SystemExit("凭据不对：" + resp.json()["message"])

result = resp.json()
if result["status"] == "SUCCESS":
    print(result["stdout"])
elif result["status"] == "COMPILE_ERROR":
    print("编译没过：", result["compileOutput"])
else:
    print(f'{result["status"]}: {result["message"]}')
    print(result["stderr"])
```

### JavaScript（Node）

```javascript
const resp = await fetch("http://localhost:8080/api/v1/executions", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "X-API-Key": process.env.EXECUTOR_AUTH_KEYS_0_VALUE,
  },
  body: JSON.stringify({ language: "javascript", code: "console.log(1+1)" }),
});
const result = await resp.json();
console.log(result.stdout);
```

### 调用方检查清单

一个健壮的调用方应该：

1. **同时检查 HTTP 状态码和 `status` 字段**——它们回答的是两个不同的问题
2. **处理 401**：凭据问题不要重试，检查 key 是不是配错了或轮换了
3. **处理 429**：退避重试（比如指数退避），不要立刻重试
4. **处理 503**：这是环境问题，重试也没用，直接告警
5. **检查 `truncated`**：如果为 `true`，输出不完整，可能需要提示用户
6. **记录 `jobId`**：出问题时这是唯一能把一次调用和服务器上的记录对上的东西
7. **给 HTTP 客户端设超时**：至少 `最长编译超时 + 最长运行超时 + 10s`
8. **不要把 key 打进日志**，也不要在前端代码里硬编码

## 限流与超时

### 并发限制

执行器有一个**并发上限**（默认 4）。超出时不会排队，而是**立刻返回 429**：

```json
{
  "status": 429,
  "message": "执行器并发已满（上限 4），请稍后重试"
}
```

**为什么排队不好？** 排队会让延迟变得不可预测：同一段代码空闲时 1 秒返回，
繁忙时 30 秒返回。这种接口通常是被别的服务调用的，
调用方更需要"快速失败然后重试"，而不是"挂在那里慢慢等"。

真要排队，应该由**调用方**用消息队列自己做，那样重试、优先级、超时都更好控制。

### 时间限制

| 阶段 | 默认上限 | 配置项 |
|---|---|---|
| 写入源码 | 10 秒 | 硬编码，正常远小于 1 秒 |
| 编译 | 按语言（Java 20 秒） | `compile-timeout-ms` |
| 运行 | 按语言（Python 5 秒） | `run-timeout-ms` |

超时的处理方式是**把整个容器 KILL 掉**，而不是只杀子进程——
用户代码可能 fork 出一串子进程，杀一个没用。

### 资源限制（按语言）

| 语言 | 内存 | 进程数 |
|---|---|---|
| Java | 256 MB | 64 |
| Python | 128 MB | 32 |
| JavaScript | 192 MB | 32 |

> Java 多给了一倍内存，因为 JVM 自己就要占一份；
> 同时运行命令里带了 `-Xmx64m`，让 JVM 在容器被内核杀之前先抛 `OutOfMemoryError`——
> 那样错误信息对用户更友好。
